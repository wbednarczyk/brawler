# ADR 0053: Research Cockpit — Dockview as the App-Wide Docking Shell

Status: **Superseded (2026-08-28) by [ADR 0108](0108-retire-docking-engine.md)** — the docking engine is retired; previously amended by [ADR 0054](0054-mode-based-thesis-centric-shell.md)

> **Revision (2026-06-23): dockview re-scoped from the app-wide shell to a workspace engine.** Real owner use showed the app-wide freeform grid feels overwhelming and directionless for a non-professional investor (a generic 2×2 with no focal point, full screens crammed into cells, the superpowers buried). [ADR 0054](0054-mode-based-thesis-centric-shell.md) keeps dockview but moves it from "the whole app shell" to the **engine of the Company-workspace (deep-dive) and Compare modes** inside a **mode-based, thesis-centric shell** (Today/Pulse home · Company workspace · Compare · Focus reader/writer), with the command palette + global semantic search as the spine. Everything built here (the `CockpitSelectionContext` store, `cockpit_layouts` persistence, the command palette, accessible tabs/keyboard model, pop-out, task presets, the section-gated-data fix) carries forward into those modes — the change is *where* dockview is used, not *whether*. The decisions below stand for the workspace/compare modes; the "app-wide shell / retire top-nav as a generic grid" framing is superseded by ADR 0054.

Supersedes (on completion): [ADR 0047](0047-top-navigation-bar.md) (top navigation bar — the single-screen-at-a-time model the cockpit replaces). Extends [ADR 0037](0037-ui-component-framework-and-authoring-contract.md) (UI framework), [ADR 0006](0006-theme-and-visual-direction.md) (`night-neon`). Related: [ADR 0038](0038-enforcement-as-guardrails.md) (enforcement), [ADR 0044](0044-report-season-cockpit.md), [ADR 0052](0052-report-over-report-diff.md), [ADR 0018](0018-import-export-boundaries.md). Roadmap: the cockpit epic; reuses the command palette (`v0.48.0`) and is the host for cross-company comparison (`v0.53.0`).

## Context

Brawler is a power-user investor research tool, but its shell is one-screen-at-a-time (the top-nav of ADR 0047). The recurring needs — read a report-over-report diff side by side (ADR 0052), compare companies (`v0.53.0`), triage the feed with a command palette (`v0.48.0`), the report-season cockpit (ADR 0044), and the tall/narrow ultrawide-quarter window — all want one missing capability: a **user-arrangeable, multi-panel workspace** (cf. Bloomberg Terminal / trading platforms / IDEs).

A pilot of [dockview](https://dockview.dev) on the *inline* company workspace was rejected **as a host** (nested scroll, fixed height, div-tab a11y) — but that was the host, not the framework. A second, full-screen spike then proved the model works on a correct host: a **linked** triage cockpit (feed selection drives the inspector + the company's claims/diff), a rich Fundamentals KPI panel, accessible tabs (axe-clean), a command palette, named saved layouts, and pop-out/float/maximize. The spike is **throwaway proof-of-concept**; this ADR records the decision to build it **properly, from scratch, as an epic**.

## Framework evaluation (research)

| Framework | Licence / local | Docking | Pop-out to OS window | a11y | Maintenance | Verdict |
| --- | --- | --- | --- | --- | --- | --- |
| **dockview** | MIT, zero-dep, React/Vue/Angular/vanilla | full (edge-dock, floating, grid, splits, named groups) | yes (`window.open`) | weak defaults but **tab/header components are replaceable** → inject accessible tabs (done, axe-clean) | **most active** (v6.6.x, React 19, ~99k wk dl — highest, 1 maintainer) | **chosen** |
| FlexLayout (caplin) | MIT, dep=React | tabsets, floating | partial | **no a11y at all** (open issue #511), not injectable | slower | worse a11y, fewer features |
| react-mosaic | MIT | **tiling only** (i3-style), tabs as node | **no** | undocumented | OK | drops the floating/pop-out (ultrawide) story |
| golden-layout | MIT | full, mature | yes | weak, vanilla-first | older, awkward React | not React-native |
| rc-dock | MIT | docking | no | weak | **stale** (alpha, 8 mo) | rejected |

**Category finding:** weak built-in accessibility is true of *every* docking library — it is not a dockview-specific defect. dockview is in fact the best of the field for a11y because its tab/header components are fully replaceable, so Brawler injects its own accessible controls (already proven in the spike). dockview also leads on features (the only one with edge-dock + floating + pop-out + persistence + replaceable chrome), adoption, and activity, is MIT / local / no-network / no-telemetry (privacy posture), React 19-ready, and is used in real trading platforms — Brawler's exact shape.

## Decision

Adopt **`DockviewReact` as Brawler's application shell**, behind the `src/screens/Cockpit/` adapter (`DockLayout`), via a phased migration that replaces the ADR-0047 top-nav. Locked decisions:

1. **Full cockpit, gradual migration, one epic** *(decision 1A)*. The end state is a docking canvas as the primary shell. The migration runs **gradually within this single epic**: foundation → migrate screens into panels one at a time (app always working) → retire the top-nav as the closing task. Not big-bang; not a permanent side-mode. **The epic is cross-cutting and carries no `milestone:vX.Y.0` label** (like the Test-architecture and Architecture-v2 foundational epics) — a single version slot would contradict the inherently multi-milestone gradual migration. Sequence: the foundation lands right after `v0.48.0` (reusing its command palette); screens migrate incrementally; the top-nav is retired and ADR 0047 superseded before `v0.53.0` Cross-company KPI comparison, its host.
2. **Floating now, pop-out after Tauri validation** *(decision 2A)*. In-app floating groups ship first (DOM overlay, always works). Pop-out to a separate OS window is gated behind a sub-spike that validates the bridge to Tauri's `WebviewWindow` (Tauri intercepts `window.open`; it needs `core:webview:allow-create-webview-window` + likely a native bridge), then enabled.
3. **Layouts persist in the data model (SQLite)** *(decision 3A)*. Named saved layouts are durable user state in a `cockpit_layouts` table, with **versioning of the serialized dockview JSON** and a safe fallback when a stored layout references a removed panel/company, and inclusion in the import/export bundle ([ADR 0018](0018-import-export-boundaries.md)). Spec in [data-model.md](../data-model.md) + [contracts.md](../contracts.md).
4. **dockview owns arrangement only; panes stay primitive-first** (ADR 0037). No inline styles. Theming is the single `.dockview-theme-brawler` bridge to `night-neon` tokens. Accessible tabs (sibling native buttons; never `role="tab"` without a tablist parent, never a control nested in an interactive element) and a full keyboard model are required before the cockpit becomes the default shell.
5. **Containment until each screen migrates** (ADR 0038). The ESLint rule confining `dockview` imports to `src/screens/Cockpit/**` stays; it widens deliberately as the shell absorbs screens, not opportunistically.
6. **Linked-panel selection flows through a single `CockpitSelectionContext` store** *(decision 6A)*. Panels react to a shared selection (a feed item drives the Inspector and the selected company's Claims/Report-diff) via **one cockpit-scoped context/store**, consistent with the Architecture-v2 per-domain view-model contexts ([ADR 0050](0050-architecture-v2-domain-stores-source-pipeline-durable-jobs.md)) — *not* per-panel controllers wired through an event bus. Rationale: the linked selection is the cockpit's reason to exist; a single source of truth is simpler, centrally testable, and avoids N×N panel coupling. Panels subscribe to the slice they need; pop-out windows (decision 2A) read the same store across the bridge. This is the architecture for phase 4.

## Risks and mitigations

- **Bus factor — single maintainer (@mathuo).** Mitigated by MIT + zero-dependency + the `DockLayout` adapter boundary (swappable without rewriting panels) + fork-ability.
- **Pop-out inside Tauri.** Validated by a dedicated sub-spike before enabling; floating works regardless; pop-out degrades gracefully if the bridge is not built. Version caveat (research, 2026-06-23): dockview **6.6.1** (current) supports basic floating + pop-out (`addFloatingGroup`/`addPopoutGroup`); **nested** floating/pop-out is **v7+**, so the phase-5 sub-spike must not assume it. Research also confirmed dockview does **not** serialize custom tab-group styling (colors/collapse) via `toJSON` — saved layouts persist geometry only (`panels_json` stays the source of truth), so the cockpit keeps tabs simple and owns any richer chrome itself.
- **Serialized-layout schema drift across dockview upgrades.** A stored layout carries a `dockview_version`; restore is wrapped with a try/fallback to a rebuilt default; a migration/normalization step is added when an upgrade changes the format.
- **a11y (category weakness).** Owned by us via replaceable chrome + a keyboard model; guarded by the `screens.a11y` axe test (cockpit already covered) and a keyboard-coverage task that is a hard gate before default-shell promotion.
- **Bundle +~67 KB gzip.** Accepted as the app-wide layout engine (not one view).

## Implementation plan (epic — gradual, from scratch)

Radicle epic `0077edd`. Phases (each a slice that keeps the app working):

1. **Foundation** — production `Cockpit` shell + `DockLayout` adapter (replacing the spike): token bridge, accessible tabs, keyboard model (focus/split/move/close), default layouts + reset, the jsdom test polyfill, a11y + broad-clickable coverage.
2. **Layout persistence contract** — `cockpit_layouts` table + commands (save/load/delete/rename), JSON versioning + safe fallback, import/export coverage. Replaces the spike's localStorage.
3. **Command palette** — the panel launcher, shared with the `v0.48.0` triage/command-palette work.
4. **Per-panel data wiring** — each screen becomes a panel, **one task per surface** (the gradual migration body), all reading the single `CockpitSelectionContext` store (decision 6A). Order:
   - **4a — linked triad first** (the cockpit's reason to exist): Feed → Inspector → Claims → Report diff, wired to the shared selection so a feed pick drives the inspector and the company's claims/diff.
   - **4b — Fundamentals** (full, editable) — the richest panel. Implemented cockpit-native by reusing the real `FundamentalsPanel` with a cockpit-owned `useCockpitFundamentals(companyId)` hook (state + the shared `useFundamentalsController`, calling `api/financials` directly) — editable for any pinned company with no AppStateRoot coupling. Editing is panel-local CRUD, not the app-wide job tracking deferred to phase 6.
   - **4c — remaining surfaces**: the company-scoped panels (Quality, Documents — plus Claims/Report-diff from 4a) reuse their self-contained `companyId` components directly. The five **global app screens** (Watchlists, Research, Notebook, Events, Report Season) are not company-scoped and own their data through per-screen view-model providers (`createScreenContext`, [ADR 0050](0050-architecture-v2-domain-stores-source-pipeline-durable-jobs.md)) whose values `AppStateRoot` builds. The cockpit hosts them as **global singleton panels** by **lifting those view-model providers to also wrap the cockpit** (the provider values are extracted to shared consts in `AppStateRoot`, used by both the top-nav section blocks and the cockpit) — this decoupling of screen-hosting from the nav shell is exactly what the phase-6 cockpit-as-host end state needs, brought forward to unblock 4c. Global panels open from the palette, are not company-scoped, and persist in `panels_json` alongside pinned/linked panels.
   - **Design (terminal-UX research, 2026-06-23).** dockview has no finance-app precedent (no "who uses" list; the one named build, GoTrader, is unconfirmed), so the cockpit's UX is borrowed from professional terminals: linked selection propagating a company across panels (IBKR TWS Mosaic color-groups, TradingView scoped sync) validates the `CockpitSelectionContext` core. Three task-shaped **default layout presets** ship as built-ins (Godel/thinkorswim/VS Code preset-workspace pattern): **Daily triage** (Feed + Inspector + Claims), **Earnings season** (Report Season + Report diff + Fundamentals + Claims), **Deep dive** (Fundamentals + Report diff + Notebook + Research, for the selected company). **Opt-in scoping**: linked panels follow the shared selection while a panel can be pinned to a specific company (TradingView scoped-sync) — the existing linked-vs-pinned split. Keep a **≤6 visible-panel ceiling**; in narrow/tall windows (~960–1280px ultrawide-quarter) degrade to stacked tabs rather than cramming. Presets compose panels as they land (4a/4b first; full set after 4c).
5. **Pop-out sub-spike + enablement** — validate the Tauri `WebviewWindow` bridge; enable OS-window pop-out or document graceful degradation. **Status (2026-06-23): bridge code landed, OS-window path NOT yet validated on Windows.** The cockpit's group pop-out (header button + `Alt+P`) goes through `popOutOrFloat` (`DockLayout.tsx`): it tries dockview's `addPopoutGroup` (which uses `window.open`) and **degrades to an in-app floating group** whenever the OS window is blocked — true in a browser/jsdom (unit-tested deterministically) and in an un-bridged Tauri. The `core:webview:allow-create-webview-window` permission is added to the main window capability (`src-tauri/capabilities/default.json`) as the prerequisite for the real path. **Still to validate on native Windows (WSL has no GUI, so it cannot be verified here):** that `window.open` actually yields a usable `WebviewWindow`, and that popped-out windows get the capabilities their panels need (a popout-window capability/label pattern) so in-panel commands still work. Until then, pop-out safely floats.
6. **Promote to default shell + slim the top-nav** — **Status (2026-06-23): done.** The Cockpit is the production default/home section (`AppStateRoot` initial `activeSection`, overridable via `App`'s `initialSection` for deep links/tests). The top-nav is **slimmed, not removed** (user decision: "default cockpit + slim menu"): the pure surfaces/workspaces the cockpit fully hosts as panels (Research, Notebooks, Events, Report Season) are dropped from the nav; **kept** are Inbox and Companies (standalone depth not yet panel-replaced — bulk triage, the full company workspace), Watchlists (a management hub the Companies screen links into), and Sources/Transcripts/Settings/Diagnostics (not in the cockpit). Those dropped values remain valid `activeSection`s (deep links + AppStateRoot still render them). **Data-loading fix (required by this):** several screens load their data only while their own section is active (`activeSection === "Research"/"Events"/"Notebooks"`); hosted as cockpit panels (`activeSection === "Cockpit"`) they rendered **empty**. The section gates in `useResearchController` and `useAppLifecycleEffects` now also fire on `"Cockpit"` so the panels load (covered by a cockpit test asserting research evidence appears). Full top-nav retirement waits until the remaining screens (Inbox/Companies/Sources/…) are panels — a later increment.

## Consequences

- ADR 0047 is **updated, not yet fully superseded**: the cockpit is the default shell and the nav is slimmed (phase 6), but a slimmed top-nav remains for the screens not yet hosted as panels. Full supersession lands when those screens migrate too.
- The spike code in `src/screens/Cockpit/` is **reference-only** and is replaced by the phase-1 production implementation; the `--dv-*` token bridge, accessible-tab approach, and the containment guardrail carry forward.
- New persistence is a data-model contract (a table, commands, a migration, import/export) — not localStorage.
- Guardrail-harvest (ADR 0045): accessible-docking-chrome and dockview-JSON-version-migration become durable rules as the phases land.
